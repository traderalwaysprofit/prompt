# Frontend Architecture V1 — Current Implementation

**Status:** current-state documentation, updated 2 September 2026.

## 1. Objective

SAMSON is a static-first prompt, workflow, and practical-tools application for `samson.web.id`. The prompt/workflow runtime remains framework-free and local-first. A narrow Cloudflare Worker layer is used only for server-side capabilities that must not expose provider credentials, beginning with B2B Prospecting AI search/enrichment.

The shell is rendered by `main.js`, which emits `samson:shell-ready`. The app-shell controller listens for this targeted event and initializes once. There is no global subtree `MutationObserver`.

Static files are still generated into `dist/`. Cloudflare invokes `worker/index.js` first only for `/api/*`; non-API requests are delegated to the `ASSETS` binding.

## 3. UI structure

- Sticky header: brand, Workflows, Prompts, and a compact More utility menu.
- Desktop More menu and mobile navigation expose Tools without adding another primary desktop navigation item.
- Hero: product statement, actions, runtime statistics, Smart Discovery card.
- Prompt library: smart search, category `select`, recommendations/recent prompts, cards, pagination.
- Prompt detail: description, example, reusable prompt, favorite, and copy controls.
- Practical Tools: `#tools` opens a registry-driven catalog.
- `#tools/google-contacts`: local Excel/CSV normalization and Google Contacts CSV export.
- `#tools/b2b-prospecting`: local-first prospect database with AI candidate review, dedupe, import/export, enrichment, and visit briefing.
- Creator/footer sections.

Tool modules follow the generic `mountTool(root, context)` lifecycle. `tools.js` retains a temporary compatibility fallback for the older Google Contacts mount export.

## 4. Runtime data contract

The browser loads and merges:

- `data/commands.json`: base commands;
- `data/commands-extra.json`: additional commands;
- `data/examples.json` + `data/examples-extra.json`: one example per runtime command;
- `data/categories.json`: active prompt categories.

A command uses the fields `id`, `name`, `categoryId`, `description`, and `template`. The old `cmd/category` field names are not part of the current contract.
Command IDs 47, 48, 50, and 52 are retired and reserved; validation rejects future reuse.

B2B Prospecting uses a separate schema-versioned local record contract and does not modify the prompt catalog data files.

## 5. Interaction model

### Prompt/workflow runtime

1. Render the static application shell.
2. Emit `samson:shell-ready` for targeted enhancement.
3. Load runtime JSON data in parallel.
4. Merge base and extra commands/examples.
5. Validate runtime data relationships.
6. Search and filter locally.
7. Persist favorites and recent commands in `localStorage`.
8. Render explicit offline/error UI when the data pipeline fails.

### Practical Tools

1. Open `#tools` and render the registry-driven catalog.
2. Lazy-load the selected tool module.
3. Mount the tool and return a `destroy()` controller for route cleanup.
4. Keep local-only processing in the browser where possible.
5. Route credentialed AI operations through same-origin `/api/tools/b2b/*` endpoints.
6. Never auto-save AI candidates; review and duplicate detection occur before persistence.

## 6. Build and Worker contract

`npm run build` recreates `dist/` and copies `index.html`, `favicon.svg`, `src/`, `data/`, downloadable `assets/`, and licensed self-hosted assets in `vendor/`.

Server-side Worker source stays outside `dist/` under `worker/`, so provider logic and configuration are not published as browser assets. `wrangler.jsonc` binds `dist/` as `ASSETS` and runs the Worker first only for `/api/*`.

The Gemini API key is an environment secret (`GEMINI_API_KEY`) and must never be committed. `AI_MODEL` is non-secret configuration.

## 7. Validation layers

- `npm run validate:data`: validates the prompt runtime contract, categories, examples, unique IDs, and cross-references.
- `npm run test:tools`: validates Google Contacts plus B2B core/storage/Worker/provider contracts with mocked provider calls.
- Baseline build: verifies static output.
- `npm run validate:security-headers`: preserves strict CSP and required response headers.
- Browser E2E on push/PR: builds and tests the current branch locally, with B2B API routes mocked.
- Browser E2E after deployment: tests `samson.web.id`.
- HTTP production validation: checks deployed entry files, runtime data, version metadata, and security headers.

No CI test consumes the real Gemini API or requires a provider key.

- multi-command composition;
- full analytics dashboard;
- drag-and-drop workflow builder;
- server-side personalization;
- framework migration (React/Vue/Svelte).
